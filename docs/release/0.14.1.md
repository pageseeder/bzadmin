# Berlioz Admin 0.14.1

Unreleased. Maintenance release of the 0.14 line, at `org.pageseeder.berlioz:pso-bzadmin:0.14.1`.
It requires Berlioz 0.14.6. Admin operations moved to an internal API, so check
[Requirements and upgrade](#requirements-and-upgrade) if the host or its proxy refers to admin URLs.

## Changes

### Redirects and forwards

- **Redirects tab.** The Config page has a Redirects tab for Berlioz's `RedirectFilter` and
  `RelocationFilter`: the status of each registration in `web.xml`, and the rules that Berlioz loaded,
  read without changing the filters. It reveals configurations that Berlioz only logs: a file that
  failed to load, a filter without a `config` parameter, rules ignored or never applied, redirects that
  the filter redirects again or that loop, a forward to an admin URL that is then denied, and a reload not applied yet. Passwords and query parameter values in
  targets are redacted. See [redirects and forwards](../guides/configuration.md#redirects-and-forwards).

### Logs

- **Logging configuration.** The Logs page has a Configuration view that says whether the application's
  logging writes events, and why not: appenders that are not started, such as a file appender that cannot
  open its file or one that stopped on a write failure, loggers with no output, logback's error and warning
  messages, and only console output. With Berlioz 0.14.6, it shows the logging files that Berlioz tried at
  startup, the one in use, and those that failed or loaded with errors. The other views show a notice when
  logging loses events or writes nowhere, and the Application page shows the verdict. Requires logback 1.5.
  See [logs](../guides/configuration.md#log-files).

### Access and security

- **Fallback login throttling.** Password checks are limited by client and overall, and excess
  requests receive `429 Too Many Requests` with `Retry-After`. Administrators already signed in are not
  affected. This addresses a [known limitation of 0.14.0](0.14.0.md#known-limitations). See
  [the fallback login](../access.md#c-the-fallback-login).
- **Password hashes from the Config page.** The Config page has a Login view that tells whether the
  fallback login has a password hash, and makes one from a password typed twice, with the configuration
  line to copy. The other views show a notice when the password is not hashed. The command-line tool
  remains. See [the fallback login](../access.md#c-the-fallback-login).
- **Development proxies.** Same-origin checks for operations prefer `Sec-Fetch-Site`, falling back to
  `Origin` for browsers that do not send it, so operations work behind a local development proxy. A
  development-only `local-proxy` setting allows the fallback login through a proxy on the same machine,
  and the log explains proxy-related refusals. See [local development proxies](../access.md#local-development-proxies).
- **System properties.** The System page also redacts sensitive parts of values whatever the property
  name, with Berlioz 0.14.6's `GetSystemProperties`: the program arguments in `sun.java.command`, the password of a URL (`jdbc:postgresql://app:[REDACTED]@db/app`)
  and parameters with sensitive names (`?password=[REDACTED]`), in every format. Paths and user names
  remain visible to administrators. See [system properties](../design/metadata-contract.md#system-properties).
- **Container challenges.** With container BASIC authentication and Berlioz 0.14.6, requests other
  than GET without credentials receive the container's challenge, on Jetty and Tomcat, so the
  [error page for 401](../access.md#error-page-for-401) that 0.14.0 hosts declared is no longer needed.
  This addresses a [known limitation of 0.14.0](0.14.0.md#known-limitations).

### Integration

- **Configuration load status.** With Berlioz 0.14.6, the Application and Config pages say when the
  global configuration failed to load or reload, and the Config page names the file that failed: Berlioz
  keeps the last valid configuration, or uses the default of every option if none loaded. **Reload
  everything** reports a failed reload of the configuration as it does for the services. The
  Application summary's `status/@configuration` is now Berlioz's load status (`ready` instead of
  `loaded`; `empty` is gone). See the [metadata contract](../design/metadata-contract.md#configuration-page-bzadmin-config).
- **Berlioz mapped by prefix.** Operations and live updates now work when Berlioz is mapped to `/html/*`
  and `/xml/*`, using `/xml/bzadmin/api/`. See [Berlioz mapped by prefix](../access.md#berlioz-mapped-by-prefix).
- **Startup check.** The overlay warns on the console, with the prefix `[BERLIOZ_INIT] WARNING`, when
  `AdminFilter` is missing or does not cover the admin services, or when Berlioz has an HTML mapping
  without the matching XML one. It registers nothing.
- **XML stylesheet.** The overlay provides `xslt/xml/bzadmin.xsl`, which removes the Berlioz header from
  XML responses. A host can override it, as for HTML. See [stylesheet overrides](../guides/configuration.md#stylesheet-overrides).
  Kickstart selects it instead of its fallback stylesheet, so it no longer logs a warning for admin XML
  responses, a [known limitation of 0.14.0](0.14.0.md#known-limitations).
- **PSML depth.** The Files page reads the metadata of PSML documents nested up to 100 elements deep,
  the default limit of Java 25, instead of 128, and reports deeper documents as too deep on every JDK.
  On Java 25, documents deeper than 100 elements were reported as malformed, with the JDK's message.
- **Filter mapping.** The documented `AdminFilter` mapping has no dispatcher elements, so it applies to
  direct requests only (`REQUEST`). Add `FORWARD` or `ERROR` only when the host forwards to admin URLs or
  uses them as error pages. See [map the filter](../access.md#1-map-the-filter).
- **Newer JDKs.** The overlay and packaged-host tests also run on Java 17, 21 and 25, with the code still
  compiled for Java 11. This addresses part of a [known limitation of 0.14.0](0.14.0.md#known-limitations).
  Java 11 remains the reference and the release build JDK.
- **Tomcat 9.** The packaged-host tests also run on Tomcat 9 (9.0.123, embedded), with the same results
  as on Jetty 10 except for the [known limitations](#known-limitations) that are specific to Tomcat.
  Jetty 10 remains the reference container. This addresses the rest of a [known limitation of 0.14.0](0.14.0.md#known-limitations).

### Caches

- **EHCache 3 statistics.** JCache caches backed by EHCache 3 show their number of entries, the
  entries and bytes of each tier (heap, off-heap, disk), and their counters whether JCache statistics
  are enabled or not, read from the statistics that EHCache keeps for each manager. Statistics are always
  on for these caches, so the page no longer offers to enable or disable them, and they can be reset at any
  time. Average times still need JCache statistics enabled. Managers that share a URI now have their
  statistics too, without average times. Tested with EHCache 3.10 and 3.12; other versions fall back to the
  statistics MBean, as before. See [integrating host caches](../guides/caches.md).

### Interface

- **Logs.** The Recent view lists events most recent first, with a button to reload them.
- **Log file selector.** The Files view groups the log files by the date in their names: undated files
  first, so the live log is selected by default instead of the oldest dated file, then daily files by
  month and monthly files by year, newest first. When the files come from more than one place, each is
  prefixed with its directory, so that two `app.log` files can be told apart. See [log files](../guides/configuration.md#log-files).
- **Recent log events.** The number of recent events held, 256 by default, can be set from 1 to 4096 with
  the global property `berlioz.admin.logs.recent-capacity`. It applies when the configuration is loaded
  or reloaded, keeping the events already captured. See [log files](../guides/configuration.md#log-files).
- **Config.** Berlioz options configured with their default value are marked "same as default".
- **System.** Rows for known memory pools (heap generations, Metaspace, code cache…) explain what their
  usage means, for HotSpot from Java 11 to 25.

## Requirements and upgrade

Java 11, Berlioz 0.14.6 or later in the 0.14 line, a Servlet 4 (`javax.servlet`) container and a
host-provided XSLT 2.0 processor. 0.14.0 required Berlioz 0.14.5.

From 0.14.0, upgrade Berlioz to 0.14.6 (`pso-berlioz` and `pso-berlioz-kickstart`), change the overlay
dependency to `0.14.1` and redeploy with exactly one overlay JAR. The
versioned JavaScript and CSS filenames change to `bzadmin-0.14.1.min.js` and `bzadmin-0.14.1.min.css`.
Access configuration and Java integration APIs are unchanged.

**Admin operations moved to `/bzadmin/api/`.** The admin pages use the new URLs, so no change is needed
when the host constrains `/bzadmin/*` as documented. Update any rule or tool that names an old URL, such
as a proxy or firewall allowlist, a script that calls an operation, or alerting on the audit log, whose
lines now show the new paths. The old URLs return 404.

| 0.14.0 | 0.14.1 |
| --- | --- |
| `POST /bzadmin/<operation>`, such as `/bzadmin/cache/clear` | `POST /bzadmin/api/<operation>`, such as `/bzadmin/api/cache/clear` |
| `GET /bzadmin/system/cpu/sample`, `/bzadmin/system/runtime/sample` | `GET /bzadmin/api/system/cpu`, `/bzadmin/api/system/runtime` |
| `GET /bzadmin/cache/info/sample` | `GET /bzadmin/api/cache/info` |
| `GET /bzadmin/system/summary`, `/bzadmin/system/cpu`, `/bzadmin/system/runtime` | `GET /bzadmin/system`, in any format |
| `GET /bzadmin/system/properties` | `GET /bzadmin/system?view=properties` |
| `GET /bzadmin/application/summary` | `GET /bzadmin/application`, in any format |
| `GET /bzadmin/service/match` | `GET /bzadmin/services/lookup` |

With Berlioz mapped by prefix, the same paths are under `/html/` and `/xml/`.

**Fallback login.** Clients that retry wrong credentials quickly may now receive `429`. Behind a proxy,
make sure the container applies the forwarded headers, otherwise every client shares the proxy's limit.

See [upgrading and rollback](../guides/upgrading.md).

## Known limitations

- Java 11 and Jetty 10 are the reference test environment; Java 17, 21 and 25 and Tomcat 9 are also tested.
- Includes of admin pages are denied. Avoid using admin URLs as container error pages; container-generated
  error responses can have different headers, and an error dispatch to an operation can execute it for an administrator.
- Log contents and service generator parameters are displayed as supplied; they must not contain secrets.
- XSLT documentation describes source declarations: it does not evaluate `use-when` or load used packages.

See [installation](../getting-started.md), [security and support](../../SECURITY.md), and
[troubleshooting](../guides/troubleshooting.md).
