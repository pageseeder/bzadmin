# Access and operation design

The host integration API and configuration examples are maintained in the [access guide](../access.md).

The host maps `AdminFilter` after authentication. It supplies an `AdminAccess` decision, uses container roles, or explicitly configures the fallback login. Permissions distinguish viewing diagnostics from performing operations. Inclusion of the JAR alone must expose no dynamic admin data.

The filter checks the route and dispatch, then places a request verdict. Overlay generators call `AdminGuard`; delegates in `org.pageseeder.bzadmin.guard` protect Berlioz generators. This second check protects services invoked outside the expected route or without the filter. The fallback password utility and login implementation stay in bzadmin as admin policy. Successful fallback credentials are cached only for the same configured username and password; changing either setting requires credentials to be verified again. Other credentials are checked within the limits of `LoginThrottle`: by client address (IPv6 by `/64` network, with a bounded number of clients tracked) and in the number of concurrent PBKDF2 computations. Throttled requests get 429 with `Retry-After`, without a check, and are audited at most once a minute so that they cannot fill the log.

The Config page makes password hashes for the fallback login on the server, with `AdminPassword`, rather than in the browser: one implementation of the hash format, tested once. The password is posted in the body to an operation of the internal API, like the BASIC credentials that the fallback login sends with every request, and is neither logged nor returned. A hash costs one PBKDF2 computation, so one is computed at a time, separately from the limits of `LoginThrottle` on logins. The page tells whether the configured password is a hash, never the password or the hash.

The hash is PBKDF2-HMAC-SHA256 (600,000 iterations, the OWASP recommendation) because every Java 11+ runtime has it: a hash made on one host is valid on any other. Argon2id is not used: no JDK provides it, so it would depend on a library on the host's classpath, and a hash made where that library is present would deny every login on a host without it. Its advantage, resistance to GPU attacks on a stolen hash, matters little for one fallback password kept in the host's configuration and checked within the limits of `LoginThrottle`. Its memory cost (tens of MiB a check) would also have to be bounded with the concurrent checks, and it is not FIPS-approved. The PHC format leaves room for another scheme (`$<scheme>$`): one added later would be accepted only where it can be verified, would report its own problem where it cannot, and would not replace PBKDF2 as the default for new hashes.

Operations use authorized POST requests. The filter checks CSRF headers/origin and restricts Berlioz control parameters to the appropriate control services. Raw output formats receive the same permission checks as HTML. Responses use no-store and an admin CSP; client code uses external scripts/styles and safe DOM construction. Follow the access guide for exact mappings, permission names and host examples.

Packaged-host tests cover filter, container BASIC and fallback integrations, anonymous and insufficient permissions, accidental inclusion, misconfiguration, dispatch paths and control attempts. See `AccessPolicyTest`, `OperationDispatchTest` and `DirectInvocationTest`.

Future framework integration is tracked in the [roadmap](../../ROADMAP.md). Retain verdict checks until a replacement framework API is released, adopted and tested.
